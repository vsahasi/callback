# The callback factor breaks Callback's phone plan

Veer's half of Callback can ship by Nov 10 on **livekit-agents 1.8.10** and Ramp's v1 Developer API, and the plan's safety design maps onto primitives that exist today: Ramp writes stay in plain Python behind one gated tool per action, step-ups run as `AgentTask`s awaited inside that tool, and challenge answers and SMS codes can be captured without ever entering the LLM's context. The plan's biggest error is the phone path. **LiveKit Phone Numbers are inbound-only**, so the callback to the number on file, which fusion rule 5 requires for every tier-2 allow and which demo call 1 depends on, cannot be dialed from the number the Stack tab picks, and no day of Veer's schedule builds it. That number's **50 free inbound minutes are a hard cap that must last through the Nov 19 final**, and the team's own test plans would use them up. A paid Telnyx number with LiveKit inbound and outbound trunks fixes all three problems for a few dollars, and it is also the only SIP route to HD voice. On the Ramp side, the Developer MCP the plan relies on for endpoint shapes now returns 404, `update-bank-accounts` adds an account that can land in `pending_approval`, and a vendor hold can come back **202 "pending approval"**, so "deny and hold" only takes effect at once if the agent also holds the vendor's open bills. The contract needs a revision on Nov 5: nothing tells the detector whom to score after a callback, OTP ownership is split across tabs, the rule against storing full phone numbers contradicts texting and dialing the number on file, a re-ask with the same idempotency key returns a stale step-up, and the agent's pinned `livekit==1.1.21` cannot share an environment with Eric's `livekit 1.2.0`. Consent needs three edits: the opening disclosure must name automated analysis by service providers, voiceprint consent needs a written element to satisfy Illinois BIPA, and LiveKit's Agent observability, if anyone turns it on, uploads every call's audio for 30 days and breaks the consent text's promise that raw audio is not kept.

## LiveKit Agents 1.8.10 already ships every primitive the gate needs

Almost everything below was read from the 1.8.10 source or from docs fetched on Nov 4–5; only the install and a few endpoint probes were actually run. The current release is **livekit-agents 1.8.10 (Oct 28, 2026)**, which supports Python 3.10 through 3.14. A 2.0.0b1 pre-release also exists, and pinning `~=1.8` keeps it out because uv skips pre-releases ([PyPI](https://pypi.org/pypi/livekit-agents/json)). On Veer's Mac the Homebrew Python 3.14 is an x86_64 build and the install failed to resolve there, while `uv pip install "livekit-agents[deepgram,openai,cartesia,silero]~=1.8"` installed 78 packages cleanly on uv-managed arm64 CPython 3.13.12 and 3.14.3 (local install log, not committed). That test left both uv interpreters in `~/.local/share/uv/python`, so `uv python pin 3.13` works immediately.

The 1.8 entrypoint is `server = AgentServer()`, `@server.rtc_session(agent_name="callback")` and `agents.cli.run_app(server)`. Setting `agent_name` turns on explicit dispatch, which LiveKit recommends for inbound SIP, and one name serves both channels: the phone dispatch rule lists it under `room_config.agents`, and browser tokens embed `RoomAgentDispatch(agent_name="callback")`, which fires only when the room is first created ([Agent dispatch](https://docs.livekit.io/agents/server/agent-dispatch.md)). The pipeline is `deepgram.STTv2(model="flux-general-en")` with `TurnHandlingOptions(turn_detection="stt")`, so Flux owns end-of-turn ([Deepgram plugin](https://docs.livekit.io/agents/models/stt/plugins/deepgram.md)), plus `openai.LLM(model="gpt-4.1")`, the plugin default, and `cartesia.TTS(model="sonic-3")` ([Cartesia plugin](https://docs.livekit.io/agents/models/tts/cartesia.md)). Pass a prewarmed Silero VAD explicitly, because the 1.8.10 release notes say "Silero is no longer loaded automatically" without saying which path changed ([release 1.8.10](https://github.com/livekit/agents/releases/tag/livekit-agents@1.8.10)). Call `ctx.wait_for_participant()` before `session.start()`, as LiveKit advises for telephony, so the disclosure in `on_enter` never plays to an empty room ([Job lifecycle](https://docs.livekit.io/agents/server/job.md)).

For browser testing, the hosted Agents Playground the plan names is gone. `lk agent dev` prints a link to the Cloud **Agent Console** instead ([Agent Console](https://docs.livekit.io/testing/agent-console.md); [LiveKit community](https://community.livekit.io/t/removing-of-https-agents-playground-livekit-io/1127)). A demo UI is `agent-starter-react` plus the project's Development token server, which LiveKit labels "for development and testing only" ([Development token server](https://docs.livekit.io/frontends/build/authentication/development-token-server.md)). The `console` mode runs with no room at all, so Eric's detector cannot join it ([Startup modes](https://docs.livekit.io/agents/server/startup-modes.md)).

### Word timestamps exist only inside a custom stt_node

The Contract wants every caller turn with word timings in Unix epoch ms. The Flux plugin keeps them: each final transcript's `SpeechData.words` carries per-word `start_time` and `end_time` in seconds from stream start, corrected across reconnects ([stt_v2.py](https://github.com/livekit/agents/blob/livekit-agents@1.8.10/livekit-plugins/livekit-plugins-deepgram/livekit/plugins/deepgram/stt_v2.py)). But **`user_input_transcribed` and `conversation_item_added` carry only plain text** ([events.py](https://github.com/livekit/agents/blob/livekit-agents@1.8.10/livekit-agents/livekit/agents/voice/events.py)), so Veer has to override `Agent.stt_node`, stamp `t0 = time.time() - frame.duration` on the first audio frame (the framework's own anchoring rule, per [audio_recognition.py](https://github.com/livekit/agents/blob/livekit-agents@1.8.10/livekit-agents/livekit/agents/voice/audio_recognition.py)), and send `round((t0 + w.start_time) * 1000)`.

The override carries a trap. **Every handoff or `AgentTask` opens a fresh Flux stream whose clock restarts at zero, and a custom `stt_node` disables the pipeline reuse that would otherwise carry the stream across** ([agent_activity.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/agent_activity.py#L1101-L1115)). Put the override in a mixin that the main agent and every step-up task inherit, or timestamps silently stop during exactly the turns Eric scores. Two smaller caveats apply. Browser sessions default to `pre_connect_audio=True`, which can push up to 3 s of pre-buffered audio and skew the first turn ([room_io/types.py](https://github.com/livekit/agents/blob/livekit-agents@1.8.10/livekit-agents/livekit/agents/voice/room_io/types.py)). And only the plugin path is verified to populate words, so do not swap in LiveKit Inference's Flux. Post turns from the `stt_node` tap rather than only from `on_user_turn_completed`, because that hook is skipped whenever the agent's current speech is uninterruptible ([agent_activity.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/agent_activity.py#L2850-L2874)).

The `/events` feed needs no extra plumbing. In the source, every session event carries `created_at` in Unix seconds, even though the docs page omits it. `agent_state_changed` into and out of `speaking` gives agent speech start and end, and the VAD-driven `user_state_changed` still fires under Flux turn detection and gives caller speech start ([events.py](https://github.com/livekit/agents/blob/livekit-agents@1.8.10/livekit-agents/livekit/agents/voice/events.py)). Whether the caller interrupted is `ChatMessage.interrupted` on the assistant item, or `agent_state == "speaking"` at the moment the caller starts. Eric should know one limit. The agent's `stopped_speaking_at` is stamped when its local audio output finishes ([agent_activity.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/agent_activity.py#L3350-L3440)), not when the caller's handset plays the last syllable, so every measured gap includes the network round trip. On phone legs that pushes the AI-caller detector's ~100 ms human baseline toward the agent range it is meant to separate.

### Step-ups run as AgentTasks awaited inside one gated tool

The plan's "use async tools" maps to `RunContext.with_filler`, which speaks a fixed line through `session.say()` once the session has been idle for `delay`, and to `ctx.update()`, which hands the LLM a synthetic tool result so it keeps talking ([Async tools](https://docs.livekit.io/agents/logic/tools/async.md)). For a security gate, use the filler and skip `update`: a premature synthetic result invites the LLM to say "done" before the gate has decided. Wrap only the HTTP call to `/authorize` in the filler, because a filler left open while a challenge waits for the caller would fire into that silence.

Each step-up is an `AgentTask[T]` awaited from inside the gated tool. **Awaiting a task anywhere except a tool body, `on_enter` or `on_exit` raises `RuntimeError`.** While a task runs, the parent pauses and holds its interruptions, and tasks run one at a time ([Tasks](https://docs.livekit.io/agents/logic/tasks.md); [agent.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/agent.py#L960-L976)). `AgentTask` has no timeout parameter, and wrapping the await in `asyncio.wait_for` breaks it: on Python 3.11 the wrapper task lacks the inline flag the await checks, and on 3.12 and later it cancels the tool and leaves the task unresolved (both read from the source, not run). Put a timer inside the task that calls `self.complete()`. The no-LLM capture turn is `session.say(phrase, allow_interruptions=False, add_to_chat_ctx=False)` followed by an `on_user_turn_completed` that completes the task and raises `StopResponse`. No LLM call runs, and neither phrase nor answer enters the chat context ([agent_activity.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/agent_activity.py#L2790-L2905)). The same pattern keeps SMS codes and spoken bank numbers away from GPT-4.1, which matters because the plan promises never to store OTP codes or full bank numbers.

One default undermines the challenge flow. **`discard_audio_if_uninterruptible` is on, so STT receives silence while an uninterruptible prompt plays, and a caller turn that ends before playout ends is dropped before the hook runs** ([turn.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/turn.py#L150-L198); [agent_activity.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/agent_activity.py#L1693-L1712)). Eric's word check accepts answers that start up to 500 ms before the prompt ends, but those words never reach Flux, so a real CFO who starts repeating digits early fails the challenge. Phrase prompts as "after I finish, repeat all of it," or disable the discard on the challenge task and accept echo risk on speakerphones. Preemptive generation is also on by default ([turn.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/turn.py#L201-L228)). Turn it off until the gate is proven, because nobody verified whether it can fire a tool call on an unfinished transcript. Ramp methods are never `@function_tool`s: the LLM sees one gated tool per action, and `generate_reply(tools=[...])` or `update_tools()` narrows the set further when risk rises ([agent_session.py](https://github.com/livekit/agents/blob/livekit-agents@1.8.10/livekit-agents/livekit/agents/voice/agent_session.py)). The sketch below assembles these verified APIs into the gate. It has not been run.

```python
class VoiceChallenge(
    TimestampedSTT, AgentTask[str | None]
):  # TimestampedSTT = the stt_node mixin
    def __init__(self, say: str, timeout: float = 30.0):
        super().__init__(
            instructions="Verification step.", llm=None
        )  # no LLM inside the task
        self._say, self._timeout = say, timeout

    async def on_enter(self):
        await self.session.say(
            self._say, allow_interruptions=False, add_to_chat_ctx=False
        )
        asyncio.get_running_loop().call_later(
            self._timeout, self._expire
        )  # tasks have no timeout arg

    def _expire(self):
        if not self.done():
            self.complete(None)

    async def on_user_turn_completed(self, turn_ctx, new_message):
        if not self.done():
            self.complete(new_message.text_content)
        raise StopResponse()  # no reply; the answer never enters chat_ctx


class Callback(TimestampedSTT, Agent):
    @function_tool()
    async def change_vendor_bank_account(
        self, ctx: RunContext[CallState], vendor_name: str
    ) -> str:
        """Change where a vendor is paid. Always requires identity verification."""
        ctx.disallow_interruptions()
        for attempt in range(4):  # new idempotency key per attempt (see audit row 17)
            try:
                async with ctx.with_filler(
                    "One moment while I verify that.", delay=0.5
                ):
                    d = await detector.authorize(
                        ctx.userdata,
                        "update_vendor_bank_account",
                        vendor_name,
                        attempt,
                        timeout=3.0,
                    )
            except Exception:
                d = Decision.deny("detector_unavailable")  # fail closed
            if d.decision == "allow":
                return await ramp_change_and_narrate(ctx.userdata, vendor_name)
            if d.decision == "deny":
                await hold_vendor_and_open_bills(ctx.userdata, vendor_name)
                return "Verification failed. Say a hold was placed and you will follow up, then end the call."
            for (
                factor
            ) in d.required_factors:  # voice_challenge, sms_otp, callback_on_file
                await run_factor(
                    factor, ctx
                )  # each awaits an AgentTask in this same asyncio task
        return "Verification did not complete. Do not make the change."
```

### Text tests skip the audio path

`session.run()` is a thin wrapper over `generate_reply()` ([agent_session.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/agent_session.py#L864-L884)), so **text-only pytest never runs `on_user_turn_completed` or the `StopResponse` capture**. Test the hook directly, capture in `llm_node` for a text-drivable variant, or copy the repo's fake-audio harness. The deterministic `FakeLLM` lives in the repo's `tests/` folder, not in the wheel ([fake_llm.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/tests/fake_llm.py)), and `mock_tools` swaps tool execution while the LLM still sees the real schemas ([Unit tests](https://docs.livekit.io/testing/unit-tests.md)). The docs say `get_job_context()` raises in tests, but 1.8.10 ships `fake_job_context()` ([testing.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/testing.py#L27-L93)). Hide the callback's SIP calls behind an injectable interface, since roomless tests cannot exercise them.

## LiveKit's free number cannot place the callback the gate requires

**"LiveKit Phone Numbers currently only supports inbound calling."** Every plan includes one free US local number, and Build adds 50 free inbound minutes ([Phone numbers](https://docs.livekit.io/telephony/start/phone-numbers/)). Those minutes are a hard cap: past it, "new requests fail rather than incurring overage charges," the allowance is shared across all of a user's free projects, and it resets on the first of the month ([Quotas and limits](https://docs.livekit.io/deploy/admin/quotas-and-limits/)). November's 50 minutes therefore have to cover integration testing, Eric's recordings and threshold calls, the Nov 10 video and the Nov 19 final. By a rough count, Eric's threshold study (12–15 people enrolled one day and tested with 10 challenges per channel on another, about 4 phone minutes each) plus his 3-call, 10-minute load test would use 80–90 minutes if run over the phone, before Veer rehearses once. A Telnyx trunk draws instead on Build's separate **1,000 third-party SIP minutes** ([LiveKit pricing](https://livekit.com/pricing)). Telnyx charges $1.00 a month per number, $0.0032 per inbound minute and $0.005 per outbound minute, but requires a paid account ([Telnyx pricing](https://telnyx.com/pricing/elastic-sip); [LiveKit Telnyx guide](https://docs.livekit.io/telephony/start/providers/telnyx/)), so start the signup on Nov 5 in case verification takes time. The Stack tab's Twilio fallback does not exist on the team's trial: Twilio SIP trunking "is only available after you upgrade" ([Twilio SIP limits](https://www.twilio.com/docs/sip-trunking/scale-and-limits)), and the trial blocks `<Stream>` and `<Dial><Sip>` ([Twilio trial voice](https://www.twilio.com/docs/usage/trials/try-out-voice)).

Telnyx also settles the HD-voice question, as far as anyone can. LiveKit's HD voice is **G.722 at 16 kHz**, and Telnyx is "the only SIP provider that supports HD voice," alongside LiveKit's own numbers ([HD voice](https://docs.livekit.io/telephony/features/hd-voice/)). Whether a given cell caller gets G.722 depends on carrier interconnects. Telnyx claims compatibility with Verizon, AT&T and T-Mobile ([Telnyx HD voice](https://telnyx.com/release-notes/experience-true-hd-voice-with-telnyx)), but **no LiveKit participant attribute or dashboard field reports the negotiated codec** ([SIP participant reference](https://docs.livekit.io/reference/telephony/sip-participant.md)). The plan's Nov 5 question about 16 kHz can only be answered by measuring energy above about 4 kHz in the detector, carrier by carrier. Keep `krisp_enabled` off on trunks and dispatch rules ([Inbound trunk](https://docs.livekit.io/telephony/accepting-calls/inbound-trunk/)) so trunk-level noise cancellation never rewrites the audio Eric scores. One audio risk the Stack tab dismisses deserves a test. It assumes the agent's synthetic voice cannot confuse the detector because Eric subscribes only to the caller's track, but LiveKit itself feeds STT silence during a 3-second AEC warm-up to avoid "contaminated/echoed audio" ([agent_session.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/agent_session.py#L118); [agent_activity.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/agent_activity.py#L1693-L1712)). On a speakerphone, the agent's Cartesia voice can land on the caller's track, and Cartesia is one of the spoofing tools Eric holds out for testing. Keep the live demo off speakerphone.

### The callback leg needs one session, a fresh identity and a contract change

LiveKit's answering-machine example shows how one session survives a hangup and a new outbound leg. Start the session with `RoomOptions(close_on_disconnect=False)`, because a caller hangup arrives as `CLIENT_INITIATED`, which otherwise closes it ([room_io/types.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/room_io/types.py#L110-L131)). After the agent says it will call back, remove the caller with `ctx.api.room.remove_participant`, then call `session.room_io.set_participant(callee_identity)` before dialing ([room_io.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/voice/room_io/room_io.py#L300-L360); [amd.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/examples/telephony/amd.py#L60-L103)). Dial with `ctx.api.sip.create_sip_participant(CreateSIPParticipantRequest(..., wait_until_answered=True), timeout=45)`, not `ctx.add_sip_participant`, which builds its request without answer detection ([job.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-agents/livekit/agents/job.py#L783-L822)). `SipCallError` maps 486/603 to a rejection, 408/480 to no answer, which does not auto-close the session, and 5xx to a trunk failure ([Outbound calls](https://docs.livekit.io/telephony/making-calls/outbound-calls.md)). Give the callee a fresh identity, because LiveKit Cloud keeps a removed participant's token cut off for 10 minutes ([LiveKit docs](https://docs.livekit.io/llms-full.txt)). Telnyx outbound trunks also need the `X-Telnyx-Username` header in `headers_to_attributes` ([LiveKit Telnyx guide](https://docs.livekit.io/telephony/start/providers/telnyx/)). Two behaviors stay unverified: whether removing a SIP participant sends a BYE and ends the PSTN leg, and whether the Flux socket, which has no keep-alive in `stt_v2`, survives a 10–45 s ring gap ([stt_v2.py](https://github.com/livekit/agents/blob/livekit-agents%401.8.10/livekit-plugins/livekit-plugins-deepgram/livekit/plugins/deepgram/stt_v2.py#L467-L530)). Test both on the day the trunk works.

Correction (Task 14b): the header goes under `headers`, which LiveKit sends on the INVITE, not only under `headers_to_attributes`, which maps headers from the 200 OK into participant attributes and does not send it. `agent/outbound-trunk.json` sets both.

The callback also exposes holes in the contract. Eric's listener subscribes "only to the caller's mic track, by identity," and the plan says "a callback re-runs the voice challenge," but the callee joins as a new participant and `/factors` only reports a result. **Nothing tells the detector to start scoring the callee.** Add a call such as `POST /v1/sessions/{id}/participant {identity, reason: "callback"}` before the re-challenge. Nothing gives the agent the E.164 number on file to dial, either; Eric's `users_on_file` holds it, so the agent needs a server-side read path. The caller ID on the callback should be the number the user dialed (`sip_number` on the request), which only works if that number is the Telnyx one. Make Telnyx the primary inbound line and keep the LiveKit number as a comparison channel for the HD claim. The callback is a new phone call, so it has to open with the recording disclosure again. The FCC also treats AI-generated voices on outbound calls as "artificial or prerecorded" voices that need prior express consent ([FCC](https://www.fcc.gov/document/fcc-makes-ai-generated-voices-robocalls-illegal)), so keep the callback strictly caller-triggered and announced. If the outbound trunk slips, Twilio Verify's `call` channel proves possession of the number on file with a keypad challenge and a spoken code ([Verify channels](https://www.twilio.com/docs/verify/authentication-channels)), but it does not re-run the voice challenge, so the pitch should not call it a callback.

### Host the live final off the free cloud plan

On Build, production agents scale to zero after the last session ends, and a cold start "adds 10 to 20 seconds before the agent joins the room." Paid plans keep agents warm ([Managing deployments](https://docs.livekit.io/deploy/agents/managing-deployments.md)). Build allows one deployment, while Ship costs $50 a month for two warm deployments and 100 LiveKit-number minutes ([LiveKit pricing](https://livekit.com/pricing)). A self-hosted worker needs no inbound ports, since it registers over an outbound WebSocket, and LiveKit hands jobs round-robin to every worker registered under an `agent_name` ([Self-hosted deployments](https://docs.livekit.io/deploy/custom/deployments/)). For the final, run `uv run agent.py start` on an always-on machine (the Veer tab's Option B), and keep the cloud deployment as a backup under a different name, such as `callback-cloud`, so two live workers never split calls. Cloud builds use the repo's Dockerfile with a 1 GB context and a 10-minute limit, inject `LIVEKIT_*` automatically and read other secrets from `--secrets-file` ([Builds](https://docs.livekit.io/deploy/agents/builds/); [Secrets](https://docs.livekit.io/deploy/agents/secrets/)).

One dispatch detail matters for privacy. Individual dispatch rules name each room after the caller's phone number plus a suffix, and LiveKit warns those names are unredacted PII ([Dispatch rule](https://docs.livekit.io/telephony/accepting-calls/dispatch-rule/)). The contract sends `room` to Eric, whose `sessions` table would then store the full number his own privacy rules forbid. Use a callee rule, which names rooms after the dialed number, or put your own UUID in dispatch metadata. Check the SIP participant's `identity` on the first call too, since its format is undocumented and is also sent to `/sessions`.

## Ramp's holds and bank changes can come back "pending approval"

The client is small. Tokens come from `POST {base}/developer/v1/token` with HTTP Basic auth and a form body. Client-credentials tokens last **10 days** and have no refresh token, and **omitting `scope` returns a token with no scopes** ([Quickstart](https://docs.ramp.com/developer-api/v1/getting-started); [Authorization](https://docs.ramp.com/developer-api/v1/authorization)). Request `vendors:read vendors:write bills:read bills:write`, add `entities:read` for creating bill fixtures ([Bill payments](https://docs.ramp.com/developer-api/v1/bill-payments)), and cache the token, since issuance is capped at 100 requests per 10 s per IP ([Rate limits](https://docs.ramp.com/developer-api/v1/rate-limiting)). Every path carries the `/developer/v1` prefix the Veer tab leaves off. The Ramp Developer MCP that the Stack, Veer and Refs tabs lean on for shapes is gone: a third-party directory listed it at `mcp.ramp.com/developer/mcp` ([Developers Digest](https://www.developersdigest.tech/mcp-servers/ramp-developer)), that URL returned HTTP 404 to an MCP `initialize` on Nov 5, and Ramp's MCP page now points coding agents at `llms.txt` ([Ramp MCP overview](https://docs.ramp.com/developer-api/v1/mcp)). Work from the OpenAPI spec ([OpenAPI](https://docs.ramp.com/openapi/developer-api.json)) and `llms-api.txt` ([API reference text](https://docs.ramp.com/llms-api.txt)) with plain httpx; the research found no official Python SDK. It also confirmed the Stack tab's reasons for not building on the hosted Ramp MCP, which signs in per user through the browser, uses no OAuth scopes and shows tools that "depend on your Ramp role and permissions" ([Ramp MCP](https://docs.ramp.com/developer-api/v1/ramp-mcp)).

`update-bank-accounts` does not change an account in place. It "adds payment details for the vendor through the approval workflow," takes `ach_details` with full account and routing numbers plus `is_default`, and returns `status: approved` or `status: pending_approval`, with a null `payment_method_id` and a `proposal_id` when approval is pending ([OpenAPI](https://docs.ramp.com/openapi/developer-api.json)). **The account surface changed on Nov 4, 2026.** List responses now include `status` and `proposal_id`, `include_pending=true` shows proposed accounts, and a pending account gets a new ID when approved ([Changelog](https://docs.ramp.com/developer-api/v1/changelog)). Retiring the old account takes a separate archive call, which needs a replacement account if bills reference the old one. Reads return only `account_number_last_four`, never routing numbers ([OpenAPI](https://docs.ramp.com/openapi/developer-api.json)). The agent's closing line therefore has to branch between "applied" and "submitted for approval." The sandbox's vendor-edit approval policy decides which one you get, and it is undocumented, so test it on day one.

Holds are the bigger surprise. **A vendor hold returns 204 when applied or 202 when "pending approval,"** with an untyped body, and the Vendor object has no hold field to read back ([OpenAPI](https://docs.ramp.com/openapi/developer-api.json)). Releasing a vendor hold reschedules nothing: payments removed during the hold "must be scheduled again." A bill hold, by contrast, returns 200 with the full Bill and "deschedules payments," and the Bill's `status_summary` enum includes `ON_HOLD`. Both pairs shipped as beta on July 15, 2026 ([Changelog](https://docs.ramp.com/developer-api/v1/changelog)), and Ramp's own metadata flags the vendor hold `x-destructive`, so "holding is always allowed" is Callback's policy rather than Ramp's. To make fail-closed literally true, the deny path should hold the vendor, hold each open bill from `GET /bills?vendor_id=…&payment_status=OPEN`, confirm `ON_HOLD` from the hold responses themselves (GETs hit read replicas), and record the hold in Callback's own tables. Holding a vendor every time a tier-1 read times out would freeze payments on every detector hiccup, so reserve automatic holds for tier-2 denials. None of these endpoints takes an idempotency key, and Ramp warns that "a timeout does not prove the operation failed" ([Rate limits](https://docs.ramp.com/developer-api/v1/rate-limiting)), so read state back before retrying any write.

The sandbox answers one of the Plan tab's open questions. Ramp Support describes access as a self-serve form that is "ready in about one minute," followed by a separate developer app inside the sandbox, which needs admin access ([Ramp Support](https://support.ramp.com/hc/en-us/articles/46681939909907-Accessing-the-Developer-API)). The documented seed data covers transactions, cards, users, departments and reimbursements, **not vendors, bills or vendor bank accounts**, so plan to create fixtures on Nov 6. API-created vendors are approved by default, and `POST /bills` needs an `entity_id` and a source account with `usage_type = BILL_PAY_BANK_ACCOUNT` from `GET /entities` ([Bill payments](https://docs.ramp.com/developer-api/v1/bill-payments)). API-created bills enter at `approval_status=APPROVED`, and the Developer API has no approval endpoint ([Bill Pay](https://docs.ramp.com/developer-api/v1/bill-pay)). That supports the Refs tab's claim that the hold is the only gate, although reviewers can approve drafts through Ramp MCP as well as the dashboard. The Contract's tier 2 lists "create or pay a bill," yet Veer's tool list has neither, and the API has no pay-a-bill call outside the beta Payments API, so drop both from the Nov 10 scope. The ⌘J "pay current bill" demo action only works on approved, scheduled bills when payment release is enabled ([Sandbox](https://docs.ramp.com/developer-api/v1/sandbox)), which should make a held bill unpayable: an untested but useful demo beat.

## Twilio's trial covers 40 codes to five phones, and Supabase wants session mode

Twilio trials no longer carry a dollar balance. They grant product units, including **40 Verify verifications and 100 SMS, expire 30 days after sign-up, and reach at most 5 verified recipients**, with the sign-up phone verified automatically and only Twilio-provided message templates ([Twilio trial](https://www.twilio.com/docs/usage/trials)). A Verify unit is spent only on a successful check, the 5-number cap is shared with Messaging and Voice, and one phone can be verified on up to three accounts, so Veer's and Eric's trials together cover about ten phones ([Try out Verify](https://www.twilio.com/docs/usage/trials/try-out-verify)). Twilio's sign-up page still promises "$15 free credits" and an "unlimited trial period," which the docs contradict, and trial texts begin "Sent from a Twilio trial account" ([Twilio sign-up](https://twilio.com/en-us/signup-credits)).

The API is three calls. Create a Service once, with `CodeLength` set explicitly because the default is undocumented ([Service](https://www.twilio.com/docs/verify/api/service)). Start a Verification with `channel="sms"` or `"call"` ([Verification](https://www.twilio.com/docs/verify/api/verification)). Then check it: the check returns `approved` or `pending`, and returns 404 once the code has expired after 10 minutes, been approved or hit the attempt limit ([Verification check](https://www.twilio.com/docs/verify/api/verification-check)). Error 60202 caps checks at five ([60202](https://www.twilio.com/docs/api/errors/60202)) and 60203 caps sends at five ([60203](https://www.twilio.com/docs/api/errors/60203)), so cancel pending verifications between rehearsals. Verify's pooled sender is exempt from A2P 10DLC registration ([Twilio blog](https://www.twilio.com/en-us/blog/migrate-programmable-messaging-to-verify)), and after the trial each success costs $0.05 plus $0.0083 per US SMS ([Verify pricing](https://www.twilio.com/en-us/verify/pricing)). The SDK is synchronous, so call it through `asyncio.to_thread`. **Ownership is unresolved.** The Plan tab gives Veer "SMS code," while the Contract routes `/otp/send` and `/otp/check` through Eric's service, Eric's Nov 8 row says "Twilio OTP," and his pins include `twilio 9.12.0`. The simplest split keeps Twilio in the detector, where the mock already answers with code 424242, and leaves Veer the spoken capture and digit normalization.

Supabase's free plan fits the demo (2 active projects, 500 MB, 200 concurrent Realtime connections), but **free projects pause after a week of inactivity** ([Supabase pricing](https://supabase.com/pricing)), so wake the project before Nov 10 and Nov 19. Eric's tab specifies asyncpg on pooler port 6543. That is transaction mode, which "doesn't support prepared statements," so asyncpg needs `statement_cache_size=0` there, while session mode on the pooler's port 5432 suits long-lived processes and runs over IPv4. The direct `db.<ref>.supabase.co` host is IPv6-only on free plans ([Supabase connections](https://supabase.com/docs/guides/database/connecting-to-postgres)). The env file's `SUPABASE_SERVICE_ROLE_KEY` is a legacy key. Supabase now issues `sb_publishable_` keys for browsers and `sb_secret_` keys for servers, which bypass RLS, and it is "deprecating the anon and service_role keys by the end of 2026" ([API keys](https://supabase.com/docs/guides/api/api-keys)). Tables created in the SQL editor do not get RLS automatically ([Supabase RLS guide](https://www.supabase.com/docs/guides/auth/row-level-security)), so enable it everywhere, then grant `select` and add a read-only `anon` policy only on the tables the dashboard reads ([Row level security](https://supabase.com/docs/guides/database/postgres/row-level-security)). The Plan tab gives Veer "Supabase logging," but Eric's persistence list already owns `sessions`, `turns` and `decisions`. Agree on one writer per table, and have Veer log the agent-side facts: tool calls, Ramp responses and hold outcomes.

The stretch dashboard is a one-day build. The agent writes rows, `alter publication supabase_realtime add table …` turns on Postgres Changes, and a `"use client"` Next.js component patches its state from `postgres_changes` events, which Realtime authorizes against RLS for each subscriber ([Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes)). Do not publish the raw `decisions` table to `anon`, because the text layer's flags carry verbatim caller quotes of up to 20 words. Publish a purpose-built table with scores and reason codes instead. Servers should write rows rather than hold a Realtime socket, since subscribing a server just to send "can multiply your Realtime bill" ([Broadcast](https://supabase.com/docs/guides/realtime/broadcast)). A browser feed straight from LiveKit's `risk` topic gives sub-second updates but needs a viewer token per browser and keeps no history ([Data packets](https://docs.livekit.io/home/client/data/packets.md)). That topic works for the agent too, with one catch. The server broadcasts data from hidden participants ([room.go](https://github.com/livekit/livekit/blob/master/pkg/rtc/room.go)), but because hidden participants are never announced, `DataPacket.participant` resolves to `None` in Python ([room.py](https://github.com/livekit/python-sdks/blob/main/livekit-rtc/livekit/rtc/room.py)), and the docs' own `data.participant.identity` example would crash on Eric's packets. Put the sender in the payload.

## Consent has to name recording, AI processors and the voiceprint

California Penal Code 632 makes recording a confidential communication "without the consent of all parties" punishable by up to **$2,500 per violation** ([Penal Code 632](https://california.public.law/codes/ca_penal_code_section_632)), and 632.7 extends all-party consent to intercepting and recording cellular calls ([Penal Code 632.7](https://california.public.law/codes/ca_penal_code_section_632.7)). In *Taylor v. ConverseNow* (N.D. Cal., Aug. 11, 2025), a court let CIPA claims proceed against an AI phone vendor under a "capability" test for third-party status ([Duane Morris](https://www.duanemorris.com/alerts/northern_district_california_allows_cipa_claims_against_ai_pizza_ordering_assistant_0825.html)). Callback streams caller audio to its own detector on Modal and to baseline APIs, so the plan's recording disclosure should name automated analysis by service providers before the caller says anything: "This is Callback, an automated assistant. This call is recorded and analyzed by automated fraud-detection systems, including our service providers." No law in force requires an inbound support agent to announce that it is an AI. California's bot law covers "online" bots with deceptive commercial intent ([B&P 17941](https://california.public.law/codes/ca_bus_and_prof_code_section_17941)), its artificial-voice rule covers prerecorded autodialer calls ([PUC 2874](https://california.public.law/codes/ca_pub_util_code_section_2874)), and AB 1609, chaptered Sept. 28, 2026, applies only to businesses with more than $500 million in revenue ([AB 1609](https://calmatters.digitaldemocracy.org/bills/ca_202520260ab1609)). The extra words cost one breath.

Voiceprints are squarely regulated in Illinois. BIPA lists "voiceprint" as a biometric identifier and defines a written release to include an electronic signature ([740 ILCS 14/10](https://codes.findlaw.com/il/chapter-740-civil-liabilities/il-st-sect-740-14-10/)). It requires a publicly available retention schedule plus written notice of purpose and term before collection ([740 ILCS 14/15](https://codes.findlaw.com/il/chapter-740-civil-liabilities/il-st-sect-740-14-15/)), with damages of **$1,000 per negligent and $5,000 per intentional violation** ([740 ILCS 14/20](https://codes.findlaw.com/il/chapter-740-civil-liabilities/il-st-sect-740-14-20/)); a 2024 amendment made repeated collection from one person a single violation ([Fisher Phillips](https://www.fisherphillips.com/en/news-insights/breaking-bipa-news-illinois-curtails-massive-damage-awards-in-biometric-cases.html)). A spoken "I agree" plausibly counts as an electronic sound, but a voice prompt is not notice "in writing." The practical answer is to enroll only California-based people, publish the Nov 30 deletion schedule in the README, and add a tap-to-agree page for anyone else.

The plan also contains two incompatible consent mechanisms. The Veer tab has the caller recite "I agree to have my voiceprint saved for verification," while the Privacy section has the agent read a longer notice ending "Do you agree?" and store the verbatim "yes." Use the Privacy text as the notice and the recited sentence as the answer, matched deterministically rather than by an LLM or a substring test for "yes." The Contract says `POST /v1/enrollments` "needs a consent record" but offers no call that creates one, so add the consent version, verbatim answer, channel and timestamp to that request.

The consent text promises "Raw audio is not kept," and LiveKit can quietly break that promise. Egress records only when someone starts it ([Egress](https://docs.livekit.io/home/egress/overview/)). But once Agent observability is enabled in project settings, LiveKit Cloud "collects transcripts, traces, logs, and audio recordings for each session," keeps them 30 days and leaves PII redaction off by default ([Agent insights](https://docs.livekit.io/testing/observability/insights.md); [Session recording](https://docs.livekit.io/testing/observability/recording.md)). Pass `record={"audio": False}` to `session.start()` on every production call, so a debugging toggle in the dashboard cannot contradict the consent text.

Correction (Ruling R11): pass `record=False`, not `record={"audio": False}`. LiveKit's recording keys all default to on, so the dict form switches off the audio alone, and the session's traces, logs and transcripts are still captured; the transcripts would hold the spoken codes and account numbers. `agent/src/callback_agent/worker.py` passes `record=False`.

## Conclusion

The research moves the risk in Veer's half. The plan treats the agent as the easy side, a LiveKit template plus a few Ramp calls, and the framework does make the gate itself straightforward. The hard parts are the seams between Veer's process and everything around it: the callee who arrives under a new identity, the prompt during which STT hears only silence, the Flux clock that restarts with every task, and the hold that Ramp can queue instead of applying. Each sits on a boundary the contract does not yet describe, which makes an hour of contract revision with Eric on Nov 5 worth more than any single day of coding that week.

The second shift is about evidence. Two claims the pitch depends on, that a denied call leaves the vendor held and that phone audio arrives in HD, cannot be taken from the docs, because Ramp can answer 202 and LiveKit never reports the codec. Both become demonstrable only once instrumented: read back `ON_HOLD` after every protective hold, measure bandwidth on every call, and show both on the dashboard beside the layer scores. The final is "judged live in person by Ramp engineers" ([Luma](https://luma.com/1gj6jag5)), people who know Bill Pay's approval semantics, so an agent that honestly says "submitted for approval" when the sandbox demands it will be more convincing than one that always says "done."
